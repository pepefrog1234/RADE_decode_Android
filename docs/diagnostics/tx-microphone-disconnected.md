# TX microphone disconnect recovery

## Evidence from the October 6 report

The radio acknowledges `set_ptt 1` at 22:57:17.210. The TX input opens on device 15,
and Java AudioTrack reports the requested USB output (device 87) as matched.
At 22:57:17.458 the TX input reports `ErrorDisconnected`. No first-microphone-frame
message follows. At 22:57:22.281 the silence filler exits with `micSeen=0`; the
output ring subsequently empties while the radio remains keyed until the operator
returns to RX.

The nonzero TX PCM RMS in this interval measures **encoded silence generated by
the filler**, not working microphone capture. This log demonstrates a lost input
stream and missing recovery; it does not establish why Android disconnected it.
The USB output routing change preceding the failure is a possible trigger that
still needs reproduction on the affected phone.

## Repair

- Poll capture health every 100 ms on a service IO worker. A disconnected input,
  no first callback within 5 seconds, or no callback for 1.5 seconds after capture
  starts triggers recovery. Silent PCM counts as live capture.
- Allow 200 ms for routing to settle, then reopen the selected microphone, with
  at most two reopens per transmission. Keep the modem and TX output alive;
  stop the old capture and filler before resetting the input filter and partial
  speech/features. Validate explicit microphone selection after reopening.
- Give each input stream its own callback token. Late callbacks from a retired
  stream cannot fail a replacement stream. Service polling is also tied to the
  exact bridge and TX generation and serialized with teardown.
- When recovery is exhausted, publish a failure while retaining TX ownership.
  The ViewModel cancels key-on retries, stops audio without EOO/drain/tail delays,
  attempts PTT OFF, then restores RX. Existing background PTT-OFF retries remain
  active if the radio does not acknowledge. Stop/disconnect invalidates automatic
  RX restoration. The UI reports the microphone failure.
- Reapply Bluetooth input effects settings to the new capture session when they
  were applied to the original session. The keep-alive RX and network TX paths
  use the same watchdog.

Oboe documents that `onErrorAfterClose` runs after the underlying stream has been
stopped and closed; recovery therefore opens a new stream rather than restarting
the closed one: [Oboe error callback reference](https://google.github.io/oboe/classoboe_1_1_audio_stream_error_callback.html).

## Verification

Host regression tests in `app/src/test/cpp/tx_input_health_test.cpp` cover capture
timeout, disconnect/reopen budgets, live silent capture, and retired callback
tokens. Run with:

```sh
c++ -std=c++11 -pthread -Iapp/src/main/cpp app/src/test/cpp/tx_input_health_test.cpp -o /tmp/tx_input_health_test
/tmp/tx_input_health_test
./gradlew testDebugUnitTest assembleDebug
```

Local verification on 2026-10-10: 147 JVM tests passed; 9 optional real-Hamlib
integration cases were skipped because `RADE_TEST_RIGCTLD` was not configured.
The six host watchdog scenarios passed with C++11 and warnings treated as errors.
The arm64 Debug APK compiled successfully. No Android device was connected.

Hardware follow-up: repeat USB RX → TX on the affected phone; confirm a
disconnect is followed by successful mic reopening and first-mic frames, and
that spoken audio reaches another receiver. Also test microphone removal,
Stop during recovery, and immediate PTT release/re-key. Persistent failure must
produce the error banner and PTT OFF, without reopening RX after Stop. Host
tests and APK compilation cannot establish the affected Android routing behavior
or over-the-air audio quality.
