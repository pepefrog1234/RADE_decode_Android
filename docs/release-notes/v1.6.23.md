# v1.6.23 — Bound Icom RX latency, optional 16 kHz RX, and CAT recovery

Version: `1.6.23-icom-rx-latency` / `versionCode 10623`.
Based on v1.6.22 (`738f73c`), including its FT-897/RX recovery fixes.

## Changes

- Prevent Monitor playback from retaining seconds of old audio after repeated
  packet loss, burst delivery or playback stalls. When its native playback
  queue exceeds 300 ms, the consumer keeps the newest 100 ms. Switching between
  Monitor and RADE also discards the previous playback source. Network RADE
  speech has a separate 800 ms ceiling, retaining 480 ms to accommodate decoded
  speech blocks. These are internal queue limits, not guarantees of total
  radio-to-phone latency.
- Bound the Icom audio delivery queue to approximately 300 ms. Discarded queue
  contents and long sequence gaps are not recreated as seconds of silence.
  Control and CI-V traffic retain their original delivery behavior.
- Add **RX audio 16 kHz (experimental)** in the Icom network settings, independent
  of the existing TX setting. The next connection requests the selected RX
  rate; PCM parsing, gap concealment and the native decimator use it. Changing
  the rate with an existing receiver rebuilds that receiver. 48 kHz remains
  the default. See the [wfview sample-rate documentation](https://wfview.org/older-user-manual-pages/preferences-file-v1-1/).
- Detect persistent radio-level CAT failures even while UDP pings/audio and
  the localhost rigctld socket remain alive. Three or more relevant Hamlib
  timeout/I/O/protocol failures spanning at least 15 seconds trigger Icom
  session recovery. Repeated OFF failure is tracked separately from healthy
  frequency responses. Late completed replies still inform this decision;
  unsupported meter commands do not trigger it. A 15-second stalled ERP
  transaction also requests Icom session recovery.
- Preserve pending PTT OFF ownership and its warning when automatic reconnect
  attempts are exhausted. Reconnecting can continue the OFF recovery; exhausting
  retries is not treated as proof that the radio has stopped transmitting.
- Add playback queue/drop counts and network queue-drop/resync/rate diagnostics
  to the existing Audio Log/CAT capture.

## Validation

- `testDebugUnitTest assembleDebug assembleDebugAndroidTest --offline` passed:
  **87 JVM tests, zero failures/errors/skips**.
- UDP fake-radio tests verify independent 16 kHz RX negotiation and PCM delivery,
  bounded backlog with a blocked consumer, and CAT-requested teardown/reconnect
  while the radio is still replying to pings.
- TCP tests verify that real ERP replies reach the recovery hook and that late
  replies still reach health tracking. Existing PTT reply-ordering tests pass.
- Host C++ ring tests passed with AddressSanitizer and UndefinedBehaviorSanitizer:
  wraparound, concurrent production/consumer trimming and five simulated minutes
  of playback stalls. The simulation retained up to **1,989 ms** with the old
  queue behavior and **290 ms** with trimming. This is a deterministic queue
  simulation, not a physical phone latency measurement.
- Android headless tests for native Monitor backlog at 16/48 kHz compile, but
  have **not run** because no Android device is attached.

## Suggested field test for Manfred

1. Keep RX at 48 kHz first. Listen in Monitor for at least 10 minutes on the same
   LTE/VPN connection and compare the delay with the radio speaker periodically.
   Brief loss can still cause an interruption; the delay should not keep growing.
2. Disconnect, enable **RX audio 16 kHz (experimental)**, and reconnect. Repeat
   the Monitor test and check RADE reception. If no audio arrives, turn this
   option off and reconnect. TX sample rate is a separate setting.
3. Repeat short TX/RX cycles and observe the physical radio's PTT indicator.
   If OFF cannot be confirmed, the warning must remain while recovery continues.
4. Export **Audio Log** immediately after a failure. Include the full interval
   from before pressing TX through RX/reconnect, plus phone model and timestamps.
   The supplied v1.6.21 excerpt ends at 20:02:33 without the final stuck-PTT
   operation, so that particular event is not yet conclusively diagnosed.
