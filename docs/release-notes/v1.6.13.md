# v1.6.13 — Icom Wi-Fi：再接続の自動リトライ + 回線切断の検出 / Auto-retry reconnects + detect a dropped link

v1.6.12（アナログ受信モニター + PTT 堅牢化）の上に積む修正です。IC-7300MK2（Icom Wi-Fi / RS-BA1 モード）で報告された、**再接続の失敗**と、**弱い LTE でのTX固着・偽の接続表示**という 2 つの残課題を対象にします。インストールは `app-debug.apk` をご利用ください。

## 症状（報告より）

**Wi-Fi モード:** 接続 → 切断 → 数秒後に再接続すると「Auth: rejected — try rebooting the radio」または「CI-V stream handshake failed」。**約 1〜2 分待つ**か、**アプリを強制終了して再起動**すると接続できる。ときどき 5 回連続でハンドシェイクエラーが出る。

**LTE モード:** QSO 中に送信が TX のまま固まり、タイムアウト後に送信が止まる。以後 IC-7300MK2 に再接続できず、Rig 画面が**矛盾した状態**になる：赤い「DISCONNECT」ボタン／緑「Connected to 127.0.0.1:4532 TX」／赤「Audio (Wi-Fi): not connected」。RX の RADE デコードは動くが、TX を押すと FreeDV 信号がスマホのスピーカーから鳴るだけで無線機に送信されない。無線機の電源を入れ直し、VPN とアプリを再起動すると回復する。

## 原因

1. **再接続が無線機の後始末レースに負けていた。** 無線機は前回セッション（ログイントークンとシリアル/音声ポート）を切断後も最大で約 1〜2 分保持します。その間に再接続すると、無線機がまだ解放していない段階で弾かれます（トークン枠なら「Auth rejected」、シリアルポート 50002 なら「CI-V stream handshake failed」）。これまではログイン段階しか再送していなかったため、これらの失敗は即エラー終了となり、操作者が手動で再試行・アプリ強制終了・時間待ちを強いられていました。

2. **UDP トランスポートの死活監視が無かった。** 弱い LTE で制御/シリアル/音声の 3 本の UDP が沈黙しても、`IcomNetworkManager` は永久に「接続中」のままでした。さらにローカルの rigctld は「死んだ pty」に対して 127.0.0.1 の TCP を維持し続けるため、`RigController` も「Connected to 127.0.0.1:4532」を表示し続け、TX 表示も固まったままに。結果として TX を押すと、Icom が接続扱いのままの瞬間はネットワーク送信、切断扱いになった瞬間はローカル出力＝スピーカー再生、という矛盾が起きていました。

## 修正内容

- **接続ハンドシェイク全体を自動リトライ**（新規ソケット・新規セッション ID・再ログイン）。バックオフ（約 1→4→8→12→16 秒）で最大 6 回試行し、無線機の後始末待ちをまたいで自動復帰します。**接続ボタンを押すだけ**で済み、強制終了や 2 分待ちは不要になりました。ユーザー名/パスワードが実際に誤っている場合だけは即座に停止します（無駄な待ち時間を避けるため）。接続中は「retrying (n/6)…」と表示されます。
- **制御ストリームの死活監視（ウォッチドッグ）を追加。** 無線機からの受信が約 15 秒途絶えたら回線切断と判断し、セッションを明示的に破棄して「Radio stopped responding — Wi-Fi/LTE link lost.」と表示します。
- **回線切断時にローカルの rig スタックを破棄。** 死んだ pty に対して「接続中」を装っていた rigctld と RigController を停止し、送信中ならエンジンと進行中の PTT リトライも停止します。これで**偽の緑「Connected」や固まった TX 表示が消え**、正しい状態から再接続できます（死んだ回線越しには unkey できないため、無線機側は自身のネットワークタイムアウトで復帰します）。

## In English

Stacks on top of v1.6.12 (analog SSB monitor + PTT hardening). Targets the two problems that remained on the IC-7300MK2 (Icom Wi-Fi / RS-BA1): **reconnects failing**, and, on weak LTE, a **hung TX with a false "connected" display**.

*Wi-Fi:* connect → disconnect → reconnect a few seconds later failed with "Auth rejected" or "CI-V stream handshake failed"; the only recovery was to wait ~1–2 minutes or kill and restart the app, sometimes after five handshake errors in a row.

*LTE:* mid-QSO the transmitter hung in TX; after a timeout it stopped, but the radio could not be reconnected and the Rig screen showed a contradictory state — a red DISCONNECT button, a green "Connected to 127.0.0.1:4532 TX", and a red "Audio (Wi-Fi): not connected". RX still decoded, but pressing TX played the FreeDV signal out of the phone's loudspeaker instead of transmitting. Only a radio power-cycle plus a VPN + app restart recovered it.

**Root causes:** (1) a reconnect that lands inside the radio's ~1–2 min session-cleanup window is rejected at whichever stage the radio hasn't freed yet (its token slot → "Auth rejected", or serial port 50002 → "CI-V stream handshake failed"), and the app only ever retried the *login* step, so it failed immediately. (2) There was no liveness check on the Icom UDP transport: when it went silent on weak LTE the manager stayed "connected" forever, and the bundled rigctld kept its 127.0.0.1 TCP link alive against a now-dead pty, so RigController kept showing a green "Connected" with a stuck TX.

**Fixed:**
- **The whole connect handshake now auto-retries** (fresh sockets, fresh session id, re-login) with backoff (~1→4→8→12→16 s, up to 6 tries), riding over the radio's cleanup window automatically — press Connect once, no app-kill or two-minute wait. A real bad username/password stops immediately; otherwise the status shows "retrying (n/6)…".
- **A control-stream watchdog** tears the session down with a clear "Radio stopped responding — Wi-Fi/LTE link lost" message after ~15 s of silence from the radio.
- **On that link loss the local rig stack is torn down** — the rigctld and its TCP client that were faking a connection against a dead pty are stopped, along with any active TX and in-flight key-on retry — so the false green "Connected" and stuck TX clear and the operator can reconnect from an honest state. (Unkeying a radio across a dead link is impossible, so the rig returns to RX on its own network timeout.)
