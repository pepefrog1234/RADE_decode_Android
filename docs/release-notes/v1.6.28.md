# v1.6.28 — 送信中の自動切断、7177→7065 kHz、受信の長い途切れ / Mid-TX disconnects, the 7177→7065 kHz jump, long RX gaps

v1.6.26/1.6.27 のフィールドレポート（IC-7300MK2、LTE+VPN）と 4 本のログへの対応です。インストールは `app-debug.apk` をご利用ください。

## 日本語

### ログから分かったこと

1. **7177 → 7065 kHz は保存データではありません。** 同梱の rigctld（Hamlib 4.5.5）は接続時や CAT エラー後に「今どちらの VFO か」を調べるため、`07 00`（VFO A 選択）を送り、周波数を読み、場合により +100 Hz して戻します。操作者が VFO B にいて、VFO A に前日の 7065 kHz が残っていれば、この探索で**無線機が VFO A に切り替わり**、7065 kHz になります。v1.6.25 のログにこの書き込みが残っています。v1.6.27 のガードはこれを遮断しますが、応答として CI-V の **NAK** を返していました。
2. **送信が数秒で切れる。** v1.6.27 のログ：LTE で `0x25` の応答を 1 通失うと Hamlib は以後すべての読み出しの前に `set_vfo` を送るモードに落ちます。ガードがそれを NAK するため、`get_freq`／`get_ptt`／`get_level` が全部 `RPRT -9`（拒否）になり、CAT 監視が「無線機が応答しない」と誤判定して 15 秒後にセッションを破棄 —— **送信中でも**。ログでは 13:37:51 と 13:40:35 の 2 回、送信中に「Radio CAT has repeatedly failed for 15 s — recovering Icom session」で送信が止まっています。PTT も音声も正常に動いていました。
3. **送信後の受信の長い途切れ。** v1.6.23 は受信の配送キューを 300 ms に制限しました。LTE 下りが 1〜2 秒止まってまとめて届くと、300 ms 分だけ残して**残りを捨てる**ため、届いていた音声が復号されません（ログでは 7 分間に約 400 パケット `queueDropped`）。

### 修正

- ガードが遮断した Hamlib の探索コマンド（VFO 選択・+100 Hz・復元）には CI-V の **OK** を返します。無線機には届かず、Hamlib は通常の読み出し経路のまま動作します。使用者の Set 要求だけが実際の周波数書き込みになります（v1.6.27 と同じ）。
- CAT 監視の復旧判定は**タイムアウト（-5）と I/O エラー（-6）だけ**を「応答なし」とみなします。NAK や手順エラーは「生きている無線機の返事」です。
- **送信中はセッション復旧を行いません**（送信・切替中・PTT 保持中は延期し、受信に戻ってから実行）。送信中は周波数のポーリングも行いません（PTT 中の Hamlib は空の応答を返し、誤判定の材料になるだけでした）。
- 受信配送キューを **2 秒**に拡大し、遅れて届いた音声は遅れて復号します（捨てません）。アナログモニター中だけは従来どおり最新 300 ms に絞ります。統計に `monitorTrim` を追加。

### 確認のお願い

- 無線機を VFO B の 7177 kHz、VFO A に別の周波数にして接続 → 数回送受信 → 切断・再接続。ダイヤルが動かないこと。
- LTE で数分の QSO 中に送信が勝手に止まらないこと。
- 受信中に短い途切れはあっても、その後の音声が復号されること（遅延が一時的に増えるのは正常）。

## English

From the v1.6.26/1.6.27 reports and four logs (IC-7300MK2 over LTE+VPN):

1. **7177 → 7065 kHz is not stored app data.** The bundled rigctld (Hamlib 4.5.5) probes "which VFO is current" at connect and after CAT errors: it sends `07 00` (select VFO A), reads the frequency, sometimes tunes +100 Hz and restores. If the operator is on VFO B and VFO A still holds yesterday's 7065 kHz, the probe *switches the radio to VFO A* — that is the jump (the v1.6.25 log shows those writes). v1.6.27's guard blocks them but replied with a CI-V **NAK**.
2. **TX cut off after a few seconds.** In the v1.6.27 log, after one lost `0x25` reply Hamlib falls back to sending `set_vfo` before every read; the guard's NAK then turned every `get_freq`/`get_ptt`/`get_level` into `RPRT -9` (rejected), the CAT-health tracker treated that as a dead radio and tore the session down after 15 s — twice **during TX** (13:37:51, 13:40:35: "Radio CAT has repeatedly failed for 15 s — recovering Icom session") while PTT and audio were working.
3. **Long RX gap after TX.** v1.6.23 bounded the RX delivery queue to 300 ms; after a 1–2 s downlink stall the arriving burst was cut to 300 ms and the rest discarded (~400 `queueDropped` packets in 7 minutes) — audio that had arrived was never decoded.

**Fixed:** blocked Hamlib probes are answered with a CI-V **OK** (never forwarded to the radio), so Hamlib stays on its normal read path; only an explicit user Set writes a frequency, as in v1.6.27. CAT-health recovery counts only timeouts (-5) and I/O errors (-6); a NAK or protocol error is an answer from a live radio. Session recovery is **never run during an over** (deferred until RX), and the frequency is not polled while transmitting (Hamlib returns an empty reply during PTT). The RX delivery queue holds **2 s** so a stalled burst is decoded late but intact; the 300 ms bound applies only while the analog monitor is on (new `monitorTrim` counter).

**Please check:** VFO B at 7177 kHz with a different frequency in VFO A → connect, several overs, disconnect/reconnect: the dial must not move. A multi-minute LTE QSO must not stop transmitting by itself. After a short RX gap the following audio should decode (a temporary latency increase is expected).

## 繁體中文

7177→7065 kHz 不是 app 儲存的資料：同梱的 rigctld（Hamlib 4.5.5）在連線與 CAT 錯誤後會用 `07 00` 選 VFO A 來探測目前 VFO，若操作者在 VFO B 而 VFO A 存著 7065，電台就被切到 VFO A。v1.6.27 的守衛擋下了這些寫入但回 NAK；LTE 掉一則 0x25 回覆後 Hamlib 改為每次讀取前先 `set_vfo`，全部被 NAK 成 `RPRT -9`，CAT 健康判定誤認電台死掉，15 秒後在**發射中**拆除 session（log 中兩次）。另外 v1.6.23 把接收配送佇列限制在 300 ms，下行停頓後的一整批音訊大多被丟棄。修正：擋下的探測改回 CI-V OK；只有 -5/-6 算斷線；發射中不做 session 復原、不輪詢頻率；接收佇列放大到 2 秒，僅類比監聽時維持 300 ms。
