# v1.6.2 — 緊急修正：V2 受信時のクラッシュ

**v1.6.0 / v1.6.1 で RADE V2 を ON にして信号を受信すると、SYNC の瞬間にアプリが落ちる問題を修正しました。** ご迷惑をおかけしました。V2 をお試しの方は必ずこのバージョンへ更新してください。

## 原因

RADE V2 のデコーダーは、opus の NN 実行部（nnet.c）のバッファ上限（1536）を超える大きさの畳み込み層（1792 入力）を使います。upstream の radae_nopy はこの上限を 2048 に引き上げる opus 用パッチ（`opus-nnet.c.diff`）を同梱していますが、v1.6.0 の取り込み時にこのパッチの適用が漏れていました。その結果、V2 信号に SYNC してデコーダーが動き出した瞬間に内部アサートで強制終了していました（V1 はこの上限内に収まるため影響なし）。

## 修正と検証

- opus の `MAX_CONV_INPUTS_ALL` を upstream パッチどおり 2048 に引き上げ
- ホスト上で V1／V2 両方の tx→rx ループバック（SYNC → デコード → EOO まで、AddressSanitizer 有効）を実行するチェックツール `tools/radecheck` を追加し、両波形とも正常完走を確認
  - v1.6.0 リリース時にはこの「実際に信号を受信する」検証が存在せず、ビルド成功のみで出荷したことが原因でした。以後、radae 更新時はこのチェックを必須にします
- V1 の動作はこの修正の影響を受けません（ループバックで確認済み）

## English summary

Emergency fix: with RADE V2 enabled, v1.6.0/v1.6.1 crashed the moment a V2
signal achieved sync. The V2 decoder uses conv layers with 1792 inputs,
exceeding opus nnet.c's MAX_CONV_INPUTS_ALL (1536); upstream radae_nopy
ships an opus patch raising it to 2048 (opus-nnet.c.diff) which was missed
during the v1.6.0 vendoring, so celt_assert aborted on the first decoded V2
frame. Fixed per the upstream patch and verified with a new host-side
tx→rx loopback harness (tools/radecheck) that runs both waveforms through
sync/decode/EOO under AddressSanitizer — V1 confirmed unaffected, V2 now
decodes cleanly. This harness is now a required gate for future radae
updates.
