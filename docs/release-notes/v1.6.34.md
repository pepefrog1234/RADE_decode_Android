# v1.6.34 — End-of-over callsign: 8-character transmit crash, weak-signal decoding, input checks

Finishes [issue #29](https://github.com/pepefrog1234/RADE_decode_Android/issues/29).
Its first point, the crash at the end of a received V2 over, was fixed in v1.6.32;
this release handles the other two — the callsign decoder now checks what it is
given, and the receiver passes it the symbol count the codec expects. Testing those
turned up a third fault on the transmit side, fixed here as well: a callsign of
exactly 8 characters crashed the app at the end of every transmitted V1 over.

Install the signed **`app-release.apk`** attached to this release.

## English

**Transmit**

- Fixed a crash at the end of every transmitted V1 over when the callsign has
  8 characters — the longest the Settings field accepts, for example `JH0VEQ/P`.
  While building the callsign frame, the encoder wrote the text terminator one byte
  past its buffer, and Android's hardened C library ends the process when it then
  measures that text. Callsigns of up to 7 characters were not affected. V2 sends
  no callsign and was not affected either.
- Nothing else about the transmitted signal changes: for every callsign that
  worked before, the callsign symbols handed to the modem are identical bit for bit.
- Not changed, but worth knowing if your callsign has a `/`: the callsign code
  table gives `/` the same code as `0`, so `JH0VEQ/P` is shown as `JH0VEQ0P` at the
  other end. The table is the one FreeDV's own software uses, so this app cannot
  change it alone.

**Receive (V1)**

- Slightly more callsigns are decoded from weak signals. The decoder was given the
  number of values in the end-of-over frame (180) where it expects the number of
  symbols (90). That count sets the confidence it attaches to each received bit;
  doubled, even a perfect symbol was rated beyond the top of the decoder's scale,
  which blurs the difference between solid bits and doubtful ones.
- What to expect: nothing changes on a signal that already gives a callsign every
  time. Where a callsign came through on about half the overs — an SNR reading of
  about 1 dB on the receiver screen — it now comes through on 2 to 3 more overs in
  every 100. At a reading of 4 to 5 dB, where nearly every over already gave one,
  a fifth to two fifths of the remaining misses are recovered. Wrong callsigns,
  already rare, become rarer. The measurements are below.
- The callsign decoder now refuses input it cannot use — no data, fewer than the
  56 symbols a callsign occupies, or no room for the result — instead of reading
  past the end of it. The receiver itself has not passed it such input since
  v1.6.32, so this is a safeguard and changes nothing you can see.

**Under the hood**

- `eoo_callsign_decode()` returns 0 for a null symbol or callsign pointer, fewer
  than 56 complex symbols, or a callsign buffer under 9 bytes. A buffer of 1–8
  bytes used to return success with the callsign cut to fit; 0 or less crashed.
- `RADEWrapper.eooCallsignDecode()` (not used by the app's own screens) passed the
  array length in floats as the symbol count. It now passes half of it, as the
  receiver does, so an array shorter than 112 floats is refused, not read past.
- New host checks: `app/src/test/cpp/eoo_callsign_codec_test.cpp` (round trip,
  null and short input, with a guard page so an over-read faults without a
  sanitizer), `app/src/test/cpp/eoo_callsign_snr_sweep.cpp` (the measurement
  below) and `tools/radecheck` `eoocheck` (callsigns up to the full 8 characters
  through the real modem; V2 decodes nothing).

## 繁體中文

**發射**

- 修正：呼號剛好 8 個字元時（設定欄位允許的最大長度，例如 `JH0VEQ/P`），每次
  V1 發話結束都會當機。產生呼號訊框時，呼號編碼器把字串結尾符號寫到緩衝區外
  一個位元組，而 Android 強化過的 C 函式庫在量測這段字串長度時會終止程式。
  7 個字元以內的呼號不受影響；V2 不傳送呼號，也不受影響。
- 發射訊號的其他部分沒有改變：原本可以正常運作的呼號，送進數據機的呼號符號
  與之前逐位元相同。
- 沒有改變、但呼號含有 `/` 時值得留意：呼號編碼表把 `/` 和 `0` 編成同一個
  代碼，因此 `JH0VEQ/P` 在對方端會顯示成 `JH0VEQ0P`。這張編碼表與 FreeDV 官方
  軟體使用的相同，本 app 無法單方面更改。

**接收（V1）**

- 弱訊號下能解出的呼號略為增加。解碼器要的是發話結束訊框的「符號數」（90），
  程式過去給的卻是「數值個數」（180）。這個數字決定解碼器對每個接收位元的
  信心程度；給了兩倍之後，連完美的符號都被評到超出解碼器量表的上限，可靠位元
  與可疑位元之間的差別因此變得模糊。
- 實際差異：原本每次都能解出呼號的訊號不會有任何變化。在呼號大約每兩次發話
  解出一次的強度（接收畫面的 SNR 讀數約 1 dB），現在每 100 次發話會多解出
  2 到 3 次。在讀數 4 到 5 dB、原本幾乎每次發話都解得出來的情況下，剩下解不出來
  的部分有五分之一到五分之二可以解出。本來就很少見的錯誤呼號也變得更少。
  量測結果見下方。
- 呼號解碼器現在會拒絕無法使用的輸入（沒有資料、少於呼號所需的 56 個符號、
  或沒有空間存放結果），不再讀到資料範圍之外。自 v1.6.32 起接收端本身已不會
  送出這類輸入，因此這是額外的防護，使用上看不出差異。

**內部變更**

- `eoo_callsign_decode()` 遇到符號或呼號指標為 null、複數符號少於 56 個、或呼號
  緩衝區小於 9 個位元組時回傳 0。過去 1–8 個位元組的緩衝區會回報成功，但呼號
  被截短到放得下的長度；0 以下則會當機。
- `RADEWrapper.eooCallsignDecode()`（app 本身的畫面並未使用）過去把陣列的 float
  個數當成符號數傳入，現在與接收端一樣傳入一半；少於 112 個 float 的陣列會被
  拒絕，而不是讀到陣列之外。
- 新增主機端檢查：`app/src/test/cpp/eoo_callsign_codec_test.cpp`（編解碼來回、
  null 與過短輸入；利用保護頁，不需 sanitizer 也能抓到越界讀取）、
  `app/src/test/cpp/eoo_callsign_snr_sweep.cpp`（下方的量測），以及
  `tools/radecheck` 的 `eoocheck`（長度最多到 8 個字元的呼號通過實際數據機；
  V2 不解出任何呼號）。

## 日本語

**送信**

- 修正：コールサインがちょうど 8 文字（設定欄に入力できる最大長。例：
  `JH0VEQ/P`）のとき、V1 の送信を終えるたびにアプリが落ちていました。
  コールサインのフレームを作る際に、エンコーダーが文字列の終端をバッファの
  1 バイト外に書き込み、Android の強化された C ライブラリがその文字列の長さを
  調べる時点でプロセスを停止させるためです。7 文字以下のコールサインには影響
  ありません。V2 はコールサインを送らないため、こちらも影響ありません。
- 送信される信号のそれ以外の部分は変わりません。これまで正常に動いていた
  コールサインでは、モデムに渡すコールサインのシンボルはビット単位で同一です。
- 変更していませんが、コールサインに `/` を含む場合の注意点です。コールサインの
  符号表では `/` と `0` に同じ符号が割り当てられているため、`JH0VEQ/P` は相手側で
  `JH0VEQ0P` と表示されます。この符号表は FreeDV 本家のソフトウェアと共通のもので、
  本アプリだけでは変更できません。

**受信（V1）**

- 弱い信号でデコードできるコールサインがわずかに増えます。デコーダーには
  送信終了フレームの「シンボル数」（90）を渡すべきところ、「値の個数」（180）を
  渡していました。この数は、受信した各ビットをどの程度信頼するかを決めます。
  2 倍の値では、完全なシンボルでさえデコーダーの尺度の上限を超えて評価され、
  確かなビットと怪しいビットの差があいまいになっていました。
- 実際の違い：これまで毎回コールサインが出ていた信号では何も変わりません。
  コールサインが 2 回に 1 回ほどデコードできていた強さ（受信画面の SNR 表示で
  約 1 dB）では、100 回の送信につき 2〜3 回多くデコードできます。表示が
  4〜5 dB で、すでにほぼ毎回デコードできていた場合は、失敗していたうちの
  5 分の 1 から 5 分の 2 がデコードできるようになります。もともと稀だった
  誤ったコールサインもさらに減ります。測定結果は下記のとおりです。
- コールサインのデコーダーは、使えない入力（データなし、コールサインに必要な
  56 シンボル未満、結果を格納する領域なし）を、範囲外まで読み出さずに拒否する
  ようになりました。受信側は v1.6.32 以降こうした入力を渡していないため、
  これは安全策であり、見た目の動作は変わりません。

**内部の変更**

- `eoo_callsign_decode()` は、シンボルまたはコールサインのポインターが null、
  複素シンボルが 56 個未満、コールサイン用バッファが 9 バイト未満の場合に 0 を
  返します。これまでは 1〜8 バイトのバッファでは、収まる長さに切り詰めた
  コールサインを成功として返し、0 以下ではクラッシュしていました。
- `RADEWrapper.eooCallsignDecode()`（アプリ自身の画面では未使用）は、配列の
  float の個数をシンボル数として渡していました。受信側と同じく、その半分を
  渡すようにしました。112 個未満の配列は、範囲外を読まずに拒否されます。
- ホスト上の確認を追加しました：`app/src/test/cpp/eoo_callsign_codec_test.cpp`
  （往復、null と短すぎる入力。ガードページにより sanitizer なしでも範囲外
  読み出しを検出）、`app/src/test/cpp/eoo_callsign_snr_sweep.cpp`（下記の測定）、
  `tools/radecheck` の `eoocheck`（最長の 8 文字までのコールサインを実際の
  モデムに通す。V2 では何もデコードしない）。

## Validation and limits

- **8-character callsign.** Checked on the arm64 object code Gradle builds into the
  APK, linked into a small program and run under QEMU. Built from the v1.6.32
  sources (the codec files are identical in v1.6.31), the call made at the end of
  every V1 over, `eoo_callsign_encode()`, aborts with `FORTIFY: strlen: detected
  read past end of buffer` for `JH0VEQ/P`, `VK5KVA/M` and `AB1CDEFG`, and returns
  normally for callsigns of 6 and 7 characters. Built from this release, all of
  them encode. The encoder's output for 300,000 random callsigns of 0 to 12
  characters is identical before and after on the x86-64 host, and the arm64
  build of this release produces the same output.
- **Symbol count, symbols in white noise.** `eoo_callsign_snr_sweep`, seeds 1 to 4
  with 50,000 frames each: 200,000 noisy frames per point, each decoded with both
  counts. Es/N0 is the signal-to-noise ratio of the symbols as the decoder
  receives them; through the modem that is about 1.7 dB below the SNR of the over
  in 3 kHz used in the second table. "Only before" and "only now" count the
  frames that just one of the two decoded.

  | Es/N0 | float count (before) | symbol count (now) | only before | only now |
  |------:|---------------------:|-------------------:|------------:|---------:|
  | −2 dB | 1,857 (0.93%) | 2,032 (1.02%) | 83 | 258 |
  | −1 dB | 10,463 (5.23%) | 11,252 (5.63%) | 420 | 1,209 |
  | 0 dB | 39,665 (19.8%) | 42,233 (21.1%) | 1,098 | 3,666 |
  | 1 dB | 98,657 (49.3%) | 102,979 (51.5%) | 1,753 | 6,075 |
  | 2 dB | 160,849 (80.4%) | 164,889 (82.4%) | 1,308 | 5,348 |
  | 3 dB | 191,283 (95.6%) | 193,078 (96.5%) | 408 | 2,203 |
  | 4 dB | 198,680 (99.34%) | 199,111 (99.56%) | 81 | 512 |
  | 5 dB | 199,864 (99.932%) | 199,919 (99.960%) | 15 | 70 |
  | 6 dB | 199,981 (99.990%) | 199,990 (99.995%) | 1 | 10 |

  The symbol count decoded at least as many frames at all 23 points from −3 to
  8 dB in 0.5 dB steps: more at the 20 points up to 6.5 dB, the same number at 7,
  7.5 and 8 dB, where at most 2 frames in 200,000 are lost. The difference is
  significant at each of the 19 points from −3 to 6 dB (two-sided sign test on
  the frames only one of the two decoded, p < 0.02). The largest gain is 2.2
  frames in 100, at 1.5 dB; in signal terms that is less than 0.1 dB. Between 4
  and 6 dB, where few frames are lost at all, a third to nearly a half of the
  losses are recovered (1,320 → 889 at 4 dB, 136 → 81 at 5 dB, 19 → 10 at 6 dB).
  Callsigns that passed every check but were not the one sent: 585 before and 415
  now in the 4.6 million frames, and 30 and 29 in 200,000 frames of noise alone.
- **Why.** The decoder's soft values scale with the inverse of the RMS that count
  divides. With the float count a noise-free symbol gets |LLR| 10.8, and the
  decoder's lookup table (`eoo_phi0`) treats everything from 10 up as certain;
  with the symbol count it gets 7.6.
- **The same sweep as the app is compiled.** Built with the NDK for arm64 with the
  app's flags (`-O2 -ffast-math`) and run under QEMU, the default run (3,000
  frames per point) prints exactly what the x86-64 host build prints.
- **Through the modem.** `tools/radecheck` `eoocheck`, seeds 1 to 4 with 2,500
  overs each: 10,000 overs per point, each 2.4 s of speech frames plus the
  end-of-over frame, converted to and from int16 audio as the app does, in white
  noise. SNR is the power of the speech frames over the noise in 3 kHz; the
  second column is the modem's own SNR estimate for the same overs, the number
  on the receiver screen.

  | SNR | receiver's reading | float count (before) | symbol count (now) | only before | only now |
  |----:|-------------------:|---------------------:|-------------------:|------------:|---------:|
  | 0 dB | −1.9 dB | 70 (0.70%) | 75 (0.75%) | 2 | 7 |
  | 1 dB | −0.9 dB | 578 (5.78%) | 641 (6.41%) | 20 | 83 |
  | 2 dB | 0.2 dB | 2,332 (23.3%) | 2,472 (24.7%) | 68 | 208 |
  | 3 dB | 1.3 dB | 5,829 (58.3%) | 6,084 (60.8%) | 74 | 329 |
  | 4 dB | 2.5 dB | 8,667 (86.7%) | 8,830 (88.3%) | 55 | 218 |
  | 5 dB | 3.7 dB | 9,772 (97.7%) | 9,819 (98.2%) | 6 | 53 |
  | 6 dB | 4.9 dB | 9,963 (99.63%) | 9,979 (99.79%) | 0 | 16 |
  | 8 dB | 7.3 dB | 9,998 (99.980%) | 9,998 (99.980%) | 0 | 0 |

  The symbol count decoded at least as many overs at every SNR: more at each
  point from 0 to 6 dB (significant from 1 to 6 dB, p < 10⁻⁴ at each; 7 against 2
  at 0 dB), and at 8 dB both missed the same 2 overs. The end of the over itself
  was reported on 99.84% of overs at 0 dB and on at least 99.98% from 1 dB up.
  Wrong callsigns: 6 before and 5 now in the 80,000 overs.
- **Other channels**, with a host harness that is not in the repository, 1,500
  overs per point. A second path 2 ms later at 0.7 of the amplitude, SNR 3 to
  12 dB: the symbol count decoded 97 overs the float count missed, the float count
  33 the symbol count missed, and never fewer at any SNR (50.0% against 48.2% at
  5 dB). Receiver 10 Hz off frequency, SNR 2 to 6 dB: 135 against 40, again never
  fewer (59.7% against 57.8% at 3 dB).
- **Input checks.** On the v1.6.32 code a null symbol pointer, an array shorter than
  112 floats placed against an unmapped page, a null callsign pointer and a buffer
  size of 0 or less each ended in a segmentation fault, and a size of 1 to 8
  returned success with the callsign cut to fit. All of these return 0 now.
  `eoo_callsign_codec_test` passes built as documented, under AddressSanitizer and
  UBSan (GCC 13 and Clang 18) and as arm64 with the app's flags under QEMU; on
  the v1.6.32 code it fails in each of the three. 60,000 calls with random
  lengths, values and buffer sizes on exact-size heap buffers ran clean under
  AddressSanitizer.
- `tools/radecheck`: `loopback` exit code 0 (V1 end-of-over payload 0 of 180 bits
  wrong, V2 end of over reported). `eoocheck` exit code 0: five callsigns,
  one of them 8 characters, each came back from one V1 over, and V2 reported its
  end of over and decoded nothing. On the v1.6.32 code AddressSanitizer stops
  `eoocheck` at the 8-character callsign.
- JVM unit tests: 147 passed; 9 optional real-Hamlib integration tests skipped
  because `RADE_TEST_RIGCTLD` was not configured.
- Arm64 Debug APK built with NDK 28.2; version code `10634`, version name
  `1.6.34-eoo-callsign`. The release workflow verifies the signed APK against the
  existing certificate.
- **Not verified.** No Android device or radio was connected, so nothing in this
  release has run on a phone or on the air. The transmit crash and its fix rest on
  the arm64 code under QEMU; it was not seen on a phone and no crash report for it
  was available. The decode figures are for white noise and the two cases above;
  fading and interference on a real band will move them. The `RADEWrapper`
  change compiles into the APK, but JNI code cannot run on the host and nothing in
  the app calls it.
- The `/` and `0` codes: confirmed by a round trip through this app's codec
  (`JH0VEQ/P` comes back as `JH0VEQ0P`). That FreeDV's own table has the same two
  entries was read from the freedv-gui v2.0.0 source, not tested against it.
