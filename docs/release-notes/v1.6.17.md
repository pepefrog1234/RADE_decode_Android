# v1.6.17 — Icom Wi-Fi/LTE：接続直後の切断・再接続ループの修正、送信バッファ上限、16 kHz 送信（実験） / Fix the connect→drop→"Auth rejected" loop, cap the TX buffer, experimental 16 kHz TX

v1.6.16 のフィールドレポート（IC-7300MK2、LTE+VPN）と診断ログへの対応です。インストールは `app-debug.apk` をご利用ください。

## 日本語

### ログから分かったこと

1. **接続の数秒後に切れて「Auth rejected」を繰り返す原因。** IC-7300MK2 は接続許可の状態パケット（0x90）を数 ms 間隔で **2 回**送ります。アプリの二重起動防止フラグは非同期の CI-V ハンドシェイク完了後にしか立たなかったため、2 通目で **2 本目の CI-V ストリーム**を開いていました。2 本目はポート 50002 を取れず（EADDRINUSE）、応答が無く 5 秒後に「CI-V stream handshake failed」→ 接続状態が破棄され → v1.6.13 の回線断処理が rigctld を停止 → 自動再接続 → 無線機はまだ直前のセッションを保持しているので「Auth rejected」…というループでした（ログの「6/6 を 3 回」）。さらに 2 本目が内部の `serial` 参照を上書きしたため、CI-V オープン命令が誤った ID で送られ、**接続しているのに全 CAT コマンドがタイムアウト**する状態も起きていました。閉じられないまま残ったストリームがポートとスレッドを占有し続ける漏れもありました。
2. **音声バッファ 500/800 ms は IC-7300MK2 では逆効果。** 500 ms で長い途切れ、800 ms では PTT が入っても変調が出ません。無線機側バッファの上限はおよそ 300〜400 ms です。
3. **送信中の途切れはパケットロスではなく上りの停滞。** 送信 70 秒間で受信側の欠落 0、無線機からの再送要求 0。一方で送信ポンプが 5 秒窓で 8〜18 % 少ないパケットしか送れていない区間があり、0.4〜0.9 秒の**上り停滞**（LTE/VPN）が原因です。
4. **v1.6.15 の再送要求は誤検知でした。** シリアル系で毎秒ちょうど 10 個の「欠番」が検出され、1 つも回復しませんでした。10/s は無線機の ping 周期そのもので、無線機の ping も追跡番号を消費していると考えられます。音声系はパケット長判定のバグで追跡自体が動いていませんでした。

### 修正

- **0x90 状態パケットの二重処理を防止**（同期フラグ、かつ自分が要求した後のみ許可）。二次ストリームの失敗で確立済みの接続を壊さないようにし、置き換えられたストリームも必ず閉じます（ポート 50002/50003 の EADDRINUSE 解消）。
- **音声バッファの選択肢を 150 / 200 / 300 ms に制限**（保存済みの 500/800 は 300 に丸めます）。PTT 保持時間は「バッファ + 100 ms」。
- **送信ポンプの追い付き方針を変更**：停滞後に補送するのは無線機バッファ 1 杯分だけ、残りは捨てます。無線機のバッファ上限を超えて溜め込まない（＝500 ms 設定で見えた長い途切れと同じ現象をアプリ側から起こさない）ためです。
- **再送要求と重複除去を停止（観測のみ）**。統計に `pings` / `pingFill`（欠番が ping で埋まった数）を追加し、次のログでモデルを検証します。
- **送信音声 16 kHz（実験的）**：Rig タブのスイッチ。上りデータ量が約 1/3 になります（約 860 → 約 290 kbps）。48 kHz への変換は無線機側。LTE の上りが原因なら効果が期待できます。
- **送受切替中に Start ボタンが一瞬出る**問題を修正（切替中も稼働中として表示）。
- 診断：CAT ログ取得に `NetTxPump` 行（5 秒ごと：遅延回数・最大遅れ・追い付き・破棄・**send() の最大ブロック時間**）を含めました。

### 確認のお願い（LTE+VPN）

1. まず音声バッファ **150 ms**、16 kHz **オフ**で接続し、切断→再接続が数秒で成功すること、送信→受信の切替が正常なことを確認。
2. 次に「送信音声 16 kHz」をオンにして再接続し、送信の途切れが減るかを WebSDR で確認。
3. 送信直後に 設定 → 診断 → **Capture CAT log** を取得して送ってください。`NetTxPump:` 行の `sendMax`/`sendSlow` が大きければ上り回線の停滞、`maxLate` が大きくて `sendMax` が小さければ端末側の遅れです。

## English

From the v1.6.16 field report and diagnostic logs (IC-7300MK2 over LTE+VPN):

1. **Why a fresh connection dropped after ~5 s and looped on "Auth rejected".** The IC-7300MK2 sends its 0x90 "connected" status twice within a few ms. Our re-entrancy flag was only set after the asynchronous CI-V handshake finished, so the second copy opened a **second CI-V stream**: it could not bind port 50002 (EADDRINUSE), got no reply, failed after 5 s with "CI-V stream handshake failed", which wiped the connection state → the v1.6.13 link-loss handler tore down rigctld → auto-reconnect → the radio still held the session → "Auth rejected" … (the "3 × 6/6" in the log). The second stream also overwrote the internal `serial` reference, so the CI-V open packet went out with the wrong IDs and **every CAT command timed out on an apparently connected rig**. Replaced streams were never closed and kept their ports and threads.
2. **Audio buffer 500/800 ms is harmful on the IC-7300MK2** (500 → long dropouts, 800 → PTT keyed, no modulation). The radio's TX buffer tops out around 300–400 ms.
3. **The TX dropouts are uplink stalls, not packet loss**: zero RX loss and zero retransmit requests from the radio during 70 s of TX, while the TX pump delivered 8–18 % fewer packets than real time in some 5 s windows — 0.4–0.9 s uplink stalls (LTE/VPN).
4. **v1.6.15's retransmit requests were false positives**: exactly 10 "missing" per second on the CI-V stream, none ever healed — the radio's ping rate; its pings evidently consume tracking sequence numbers. The audio stream was never tracked at all (packet-length test bug).

**Fixed:** single, synchronous guard for the 0x90 status (and only after we requested the streams); a failed secondary stream no longer destroys an established connection; every stream created is closed (no more EADDRINUSE on 50002/50003). Buffer choices limited to 150/200/300 ms (saved 500/800 clamp to 300); PTT tail = buffer + 100 ms. The TX pump now catches up at most one radio buffer after a stall and drops the rest, so it never pushes the radio past its buffer limit. Gap tracking is observe-only (no requests, no drops) with `pings`/`pingFill` counters to confirm the model. **Experimental "TX audio 16 kHz"** switch on the Rig tab — one third of the uplink bitrate; the radio converts to 48 kHz. The Start button no longer flashes during the TX→RX hand-over. Diagnostics: the CAT capture now includes the `NetTxPump` health line (late/maxLate/catchup/dropped/**sendMax/sendSlow**).

**Please test (LTE+VPN):** (1) buffer 150 ms, 16 kHz off — disconnect/reconnect should succeed within seconds and TX→RX switching should be normal; (2) enable "TX audio 16 kHz", reconnect, and compare TX dropouts on the WebSDR; (3) capture Settings → Diagnostics → CAT log right after an over. Large `sendMax`/`sendSlow` in `NetTxPump:` = the uplink stalling; large `maxLate` with small `sendMax` = the phone stalling.

## 繁體中文

從 v1.6.16 的 log 找到：IC-7300MK2 會在幾毫秒內送兩次 0x90「已連線」狀態，第二份開了第二條 CI-V 串流，握手失敗後把已建立的連線狀態清掉，觸發斷線處理與自動重連，電台又還握著 session → 一直「Auth rejected」；第二條串流還覆寫了內部參照，導致已連線卻所有 CAT 指令逾時。已修正（同步防重入、只在我方要求後才接受、失敗不破壞既有連線、所有串流確實關閉）。音訊緩衝限制為 150/200/300 ms（500/800 在此電台會造成長中斷或無調變）。發射迴圈停頓後只補送一個電台緩衝量、其餘丟棄。重傳要求改為僅觀測（原先為誤判）。新增實驗性「發射音訊 16 kHz」以降低上行流量。修正切換時 Start 按鈕閃現。診斷擷取加入 `NetTxPump` 行。
