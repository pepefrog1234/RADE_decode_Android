# Issue #33：QMX+ 按下 TX 後間歇性不發射

2026-11-18 檢查；程式基準 `09bf624`（v1.6.32）。回報時的版本為 v1.6.31。
同日取得與 APK 內建版本相同的 Hamlib 4.5.5 rigctld 後，補做實際執行的驗證並更新本文。

## 回報內容

[Issue #33](https://github.com/pepefrog1234/RADE_decode_Android/issues/33)（KD3CRX）：
QRP Labs QMX+，按下 Tx 後電台有時不進入發射，要按幾次才成功，詢問有沒有設定可以改善。

沒有附 CAT log，也沒有說明 Rig 分頁選的機型與連線方式、QMX 韌體版本，以及失敗當下
畫面有沒有出現紅字。因此下面分成「可以確認的事」和「與症狀相符、但還沒有現場紀錄
證實的推論」。

## 可以確認的事

1. **App 把 rigctld 的 `RPRT 0` 當成已經發射。** `TransceiverViewModel.doSwitchToTx()`
   送出 `set_ptt 1`，`RigController.setPtt()` 收到 `RPRT 0` 就回報成功，之後不再向電台
   確認；只有收不到回覆時才讀回狀態。

2. **對 Kenwood 協定的電台，`RPRT 0` 不代表電台收到了 `TX;`。** APK 內建的 rigctld 是
   Hamlib 4.5.5。QMX 使用的機型 2052（`rigs/kenwood/ts480.c` 的 QRPLabs 項目）以
   `kenwood_set_ptt` 發射：`kenwood_transaction()` 寫出 `TX;`，這個指令沒有回覆，所以
   緊接著寫出確認用的 `ID;`，讀到 `ID020;` 就回傳成功。下面兩種情況電台其實沒有發射，
   Hamlib 仍回報成功：
   - `TX;` 沒有送達，但後面的 `ID;` 送達了；
   - 電台用 `?;` 拒絕 `TX;`：`case '?'` 分支會再讀一次，讀到 `ID020;` 後照樣視為成功。

   Hamlib 的 `rig_set_ptt()` 裡其實有一段「設定後讀回、不符就重試」的程式，但在 4.5.5
   是以 `#if 0` 停用的（註解說 IC-9700 在 split 模式下，set_ptt 之後立刻 get_ptt 會失敗）。

3. **按下後 0.5 秒內讀回的狀態不是電台的狀態。** `rig_set_ptt()` 成功後把「ON」寫進
   500 ms 的快取，這段時間內 `rig_get_ptt()` 直接回傳快取。Kenwood 後端的 `IF;` 另有
   500 ms 快取，而且「設定指令讓快取失效」的條件式括號放錯，實際上不會失效。

4. **QMX 回報狀態的位置與 Hamlib 讀取的位置一致。** QMX CAT 手冊（韌體 1_04_003）：
   `TX;` 等同 `TQ1;`，沒有回覆；`ID;` 回 `020`；無法執行的指令回 `?;`；`IF;` 採 TS-480
   格式，「Transceiver status: 0 = RX, 1 = TX」落在回覆的 index 28，正是
   `kenwood_get_ptt()` 讀取的位置。

5. **USB 橋接層寫入失敗時不重送。** `usb_serial_helper.c` 的寫入執行緒在 `bulkTransfer`
   失敗時只記錄錯誤，那筆資料就遺失了。紀錄的標籤是 `UsbPtyBridge`，CAT log 會擷取。

6. **不是每台電台回報的狀態都能採信。** uSDX 韌體（`usdx.ino` 的 `Command_IF()`）在
   `IF;` 回覆的發射欄位固定填 `0`，而它的 `ID;` 同樣回 `020`；以 TS-480 機型連接時，
   Hamlib 在發射中也回報「接收」。

7. **S 表讀取失敗時，rigctld 會讓後面的指令（包含 key-on）等上一秒左右。** App 在接收時
   每一輪輪詢都讀一次 S 表（`get_level STRENGTH`，Hamlib 送出 `SM;`）。Hamlib 4.5.5 只
   接受「`SM` 加四個字元」的回覆；長度不符時重試三次後回報 protocol error，而 rigctld
   遇到這類錯誤會關閉電台、等一秒、再重新開啟。實測數字見下一節。

## 以真實 Hamlib 4.5.5 重現

環境：Ubuntu 24.04 的 `libhamlib-utils 4.5.5-3.2build2`，`rigctld --version` 顯示
`Hamlib 4.5.5 … SHA=6eecd3`，與 APK 內建的 rigctld 是同一個原始碼版本。以機型 2052 啟動，
接到一個依 QMX CAT 手冊回應、掛在 PTY 上的模擬電台。

**第 2、3 點（key-on）**

| 模擬電台的行為 | rigctld 對 `set_ptt 1` 的回覆 | 電台實際狀態 |
|---|---|---|
| 正常 | `RPRT 0`（2 ms） | 發射 |
| 沒收到 `TX;`，只收到 `ID;` | `RPRT 0`（2 ms） | **接收** |
| 以 `?;` 拒絕 `TX;` | `RPRT 0`（102 ms） | **接收** |

後兩種情況下，`get_ptt` 在確認後 100、300、450 ms 都回 `PTT: 1`，而且沒有向電台送出
任何指令；600 ms 時才送出 `IF;` 並回 `PTT: 0`。這時再送一次 `set_ptt 1`，電台進入發射。

**第 7 點（S 表）**

| 電台對 `SM;` 的回覆 | `get_level STRENGTH` | rigctld 被佔住的時間 | 讀取開始 50 ms 後按下的 key-on 等待 |
|---|---|---|---|
| `SM0005;`、`SM-103;`（四個字元） | 成功 | 2 ms | 2 ms |
| `?;`（不支援此指令） | `RPRT -9` | 約 0.6 秒 | 約 0.55 秒 |
| `SM27;`、`SM-73;`（不是四個字元） | `RPRT -8` | 約 1.2 秒：0.15 秒後回報失敗，接著約 1 秒重新開啟電台 | 約 1.6 秒 |
| 不回應 | `RPRT -5` | 2 秒後回報失敗，接著同樣重新開啟電台 | 約 3.5 秒 |

`-8` 與 `-5` 之後的那一秒來自 rigctld 本身（`tests/rigctld.c`：遇到非「軟性」錯誤就
`rig_close()`、睡一秒、`rig_open()`）；`-9` 屬於軟性錯誤，不會重新開啟。

再用 app 自己的 `RigController`（輪詢開啟）連上同一個 rigctld，在輪詢週期的不同位置按
八次 key-on，量「按下到電台收到 `TX;`」的時間：

| 電台對 `SM;` 的回覆 | 修正前 | 修正後 |
|---|---|---|
| 每次都是 `SM-86;` | 254、834、659、508、329、161、1、1135 ms | 全部 2 ms 以內 |
| `SM-86;` 與 `SM-103;` 交替 | 2、842、2、493、2、163、1207、1 ms | 全部 2 ms 以內 |

## 推論（尚未證實）

有兩個機制都會造成「按了沒有立刻發射、要按好幾次」，而且畫面上都沒有錯誤：

**A. `TX;` 遺失或被拒絕（第 1、2 點）。** 只要 `TX;` 在 rigctld → PTY → USB → QMX 的
任何一段遺失，或被 QMX 拒絕，app 會顯示發射中並送出音訊，電台卻留在接收。不知道
`TX;` 實際上有多常遺失。

**B. S 表輪詢佔住 CAT（第 7 點）。** 按下的時間點如果落在一次失敗的 S 表讀取之後，
key-on 會晚 0.5 到 1.6 秒才送到電台。使用者看到電台沒有反應而放開重按，就成了
「要按好幾次」。這個機制成立的前提是 QMX 對 `SM;` 的回覆不是 Hamlib 4.5.5 預期的格式，
**而這一點沒有實機可以確認**。間接的線索：
- QMX CAT 手冊只說 `SM;`「Returns the S-meter value in dB」，沒有給格式；同一份手冊裡
  其他讀數都不補零、長度不固定（`SW121;`，接收時是空的 `SW;`）。
- Hamlib 後來為 QMX 新增的專用機型只讀取 SWR 與功率表，沒有讀 S 表。
- 韌體早於 1_01_004 時沒有 `SM` 指令，會回 `?;`。
- 若回覆是帶負號的 dB 值，長度會隨訊號強度在三、四個字元之間變動，失敗就是時有時無。

B 在現行版本（v1.6.31）的 CAT log 裡看得出來：每一輪輪詢都會有一行
`CMD 'get_level STRENGTH' → RPRT -8`（或 `-9`、`-5`）。

**沒有紀錄可以證明回報者遇到的是 A、B 或其他原因。** 其他同樣可能、而且這次的修正
解決不了的原因：

- QMX 自己不允許發射。手冊記載 SWR 保護預設啟用（門檻 3），觸發後頻率右側顯示
  `S`，在保護解除前禁止發射。這種情況新版最多只能顯示紅字提示。
- 電台其實已進入發射，但沒有射頻輸出。SSB 的 Input 預設是 `Ext. mic`，要設成 `USB`
  或 `Auto` 才會取用手機送來的音訊；另外還有 TX 電平與 Android 媒體音量。
- 韌體太舊。QMX 韌體更新紀錄：SSB 模式下 `TX;` 無法發射在 1_01_001 修正，`TQ1;`
  在 1_01_003 修正。
- App 端發射音訊開啟失敗，或上一次 PTT 釋放尚未確認而拒絕新的發射。這兩種情況
  畫面會出現紅字。

## v1.6.33 的修正

針對 A：

- rigctld 確認 key-on 之後，`RigController.confirmKeyed()` 等 0.6 秒（超過上述兩個
  快取的 500 ms）再讀一次電台狀態。仍是「接收」就重送 `set_ptt 1`，最多兩次，每次
  之後再等 0.6 秒讀回。
- 重送只在「這次 key-on 仍是最新的 PTT 指令」時才會寫出。這個判斷和寫入在同一把
  傳輸鎖內完成，而放開 PTT 會先登記為更新的指令、再寫出 OFF，所以重送的 key-on
  不可能排在 OFF 之後送出；ViewModel 也照舊在送 OFF 之前取消並等待整個 key 工作結束。
- 因為第 6 點，「接收」這個讀數只有在該電台於這次連線中曾經回報「發射」之後才被
  採信並顯示提示。連線後第一次檢查仍會重送；如果重送後還是「接收」，而這台電台
  從未回報過「發射」，之後就只讀不動，直到它回報一次「發射」為止。自動重連到同一個
  rigctld 時，這項判斷會保留。
- 每一次 key-on 只檢查一次，重送的額度（兩次）屬於那次 key-on 而不是那次呼叫；
  從未送過 key-on 時，檢查不會送出任何指令。
- 已採信的電台在兩次重送後仍是「接收」時，畫面顯示紅字，請使用者檢查電台是否
  允許發射。App 不會因此中止發射或自行放開 PTT：這個判斷只依據一筆狀態讀數。
- `UsbPtyBridge` 在 USB 寫入失敗時，多記錄沒有送出的位元組。

針對 B：

- S 表讀取一失敗，輪詢就暫停讀它 30 秒；之後每次失敗暫停時間加倍，最長 5 分鐘。
  連續五次讀取成功才把失敗紀錄歸零，所以「時好時壞」的 S 表不會因為偶爾成功一次就
  回到每輪都讀（`MeterPollBackoff`）。暫停期間 Rig 分頁的 S 表停在最後一次讀到的值。

## 沒有修改的部分

- **USB 橋接層不重送。** 沒有證據顯示寫入曾經失敗；盲目重送可能讓同一個指令送達
  兩次或延遲送達。上面的狀態檢查不論 `TX;` 在哪一段遺失都有效，新增的紀錄則可以
  判斷寫入是否真的失敗。
- **放開 PTT 沒有同樣的檢查。** USB 連線的電台，OFF 仍只看 rigctld 的確認
  （Hamlib 對 `RX;` 連 `ID;` 都不檢查）。OFF 的誤判會讓下一次發射被拒絕，風險不同，
  需要另外評估。
- **第一次發射之前無法判斷。** 整個連線期間從未成功發射過的電台不會出現紅字提示，
  因為這時分不出「沒有發射」和「不會回報發射」。
- **分不出「沒有發射」和「發射後又掉回接收」。** 電台在發射開始後一兩秒內自己回到
  接收（保護動作，或在電台上取消發射），app 會再送 key-on，最多兩次。
- **其他輪詢指令沒有同樣的暫停。** 頻率、PTT 與模式的讀取照舊每輪進行；它們失敗時
  rigctld 一樣會重新開啟電台，但這些讀數是控制所必需的，另由 `RigCatHealth` 處理。
- **S 表本身沒有修好。** 如果 QMX 的 `SM;` 回覆確實不合 Hamlib 4.5.5 的格式，Rig 分頁
  的 S 表就讀不到值；這次只是不再讓它拖慢其他指令。

## 驗證與界線

- 設定 `RADE_TEST_RIGCTLD=/usr/bin/rigctld`（上述 Hamlib 4.5.5）執行：185 項測試全數
  通過，沒有略過。其中包含原有的 9 項 Icom 整合測試，以及新增的 5 項
  `HamlibKenwoodPttTest`：正常 key-on 不重送、`TX;` 遺失與被 `?;` 拒絕時 Hamlib 仍確認
  而檢查會重送成功、S 表回覆被拒（每次，以及時有時無）時 key-on 不再被拖延。
- 未設定時：171 項通過、14 項略過（就是那 14 項需要真實 Hamlib 的測試）。
- 單元測試以模擬的 rigctld 驗證：確認後仍回報接收會重送並成功、已採信的電台持續
  接收回傳失敗且不送 OFF、從不回報發射的電台只在第一次發射重送、狀態讀不到時不
  動作、放開後不再送 key-on（包含「狀態檢查通過之後才放開」）、取消後不送任何
  指令、重送未獲回覆時不下結論、沒有 key-on 或已檢查過時不動作、S 表失敗後輪詢
  不再讀它。
- 把保護逐項拿掉來檢驗測試本身：存疑後只讀不動、未採信時不下結論、重送前的
  「仍是最新指令」判斷、傳輸層在寫入鎖內才詢問、重送未獲回覆即停止、每個 key-on
  只檢查一次、未送過 key-on 不動作、重連時是否保留判斷、S 表輪詢的暫停，各自拿掉後
  對應的測試都會失敗。
- 第一版提交後另請一個獨立的審查，沒有找到「放開後還送出 key-on」的路徑，但指出
  上述保護當時有一層沒有被測試到、未送過 key-on 時會誤送、紀錄會顯示沒送出的指令、
  以及一個協程洩漏；這四點都已修正，前三點補上了測試（ViewModel 沒有單元測試，
  協程洩漏那一點只有程式審查）。
- 另以一支不在版本庫內的壓力測試，讓「放開」與「檢查／重送」以隨機時序競爭
  42,000 次，再混入輪詢、取消與重連 3,000 次：沒有任何一次 key-on 出現在 OFF 之後，
  同一個 key-on 也從未重送超過兩次。
- 沒有連接 Android 裝置或 QMX。模擬電台是照 QMX 手冊寫的，不是 QMX：QMX 在 SSB
  發射中 `IF;` 的實際回覆、`SM;` 的實際格式、`TX;` 是否真的會遺失、這些修正能否解決
  回報者的問題，都還沒有實機確認。
- Hamlib 是用 Ubuntu 的套件，不是自行從原始碼建置（在這個環境建置被權限檢查擋下）。
  套件與 APK 內建的 rigctld 回報相同的版本與 SHA，但不是同一個二進位檔。
- 成功補救的那次發射，開頭大約 0.7 秒（重送兩次時約 1.5 秒）沒有送出。

## 需要回報者提供

1. Rig 分頁選的機型（應為 QRP Labs QMX/QDX）、連線方式與鮑率，QMX 韌體版本。
2. 失敗時畫面有沒有紅字；QMX 螢幕上有沒有 `S`（SWR 保護）或發射指示。
3. 設定 → 診斷：先按「清除」，重現一次失敗後立刻「擷取 CAT 紀錄」。要看的是：
   - `CMD 'get_level STRENGTH' → RPRT -8`（或 `-9`、`-5`）是否每一輪都出現：機制 B；
   - `setPtt(true) … elapsedMs=` 的數字是否偶爾到幾百毫秒以上：key-on 被拖延；
   - `UsbPtyBridge` 的 `bulkTransfer returned`：USB 寫入失敗；
   - 新版另有 `confirmKeyed: rig reports …` 與 `keyed again`：機制 A。
4. QMX 的 SSB Input 是否為 `USB` 或 `Auto`、VOX 是否關閉。
